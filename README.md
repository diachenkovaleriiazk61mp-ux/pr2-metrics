# Лабораторна робота 2 Метрики сервісу і межа масштабованості

Варіант 7. Дьяченко Валерія, ЗК-61мп.

Проєкт другої лабораторної роботи. Сервіс зберігає записи про вакцинацію, як у першій роботі. До нього додано Prometheus, ступінчастий генератор і розрахунок універсального закону масштабованості. Репозиторій першої роботи: https://github.com/diachenkovaleriiazk61mp-ux/pr1-CRUD-- . Код третьої роботи сюди не входить.

**Результати:** виконано запуски в Docker на 1–4 екземплярах. Виміряно X(1)=270.333, X(2)=427.800, X(3)=596.733 та X(4)=633.867 rps. SIGTERM перевірено: код завершення 0, у перевіреному вікні 2002 відповіді 200 і жодної помилки. Повний опис і висновки — у `REPORT.md`, числовий додаток — у `RESULTS.md`.

## Запуск у Windows

Потрібні Docker Desktop у режимі Linux containers і Python 3.10–3.13. Відкрий PowerShell у розпакованій папці проєкту:

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

API: http://localhost:18081/healthz . Prometheus Targets: http://localhost:19090/targets . Для іншого числа екземплярів:

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1 -Replicas 4
```

У Targets мають з’явитися чотири цілі `web` зі станом UP. Збережи скриншот цієї сторінки в `figures/targets-4.png`, поки запущено чотири екземпляри.

Для Linux/macOS: `sh start.sh` або `sh start.sh 4`.

Пароль генерується автоматично в `.env`. Порти другої роботи — 18081 і 19090; томи мають префікс `vaccinations-pr2`, тому не збігаються з першою роботою. Якщо `.env` уже створено, його пароль зберігається. Не замінюй пароль після ініціалізації бази.

## Вимірювання

На комп’ютері з Docker виконай:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lab.txt
.\.venv\Scripts\python.exe scripts/experiment.py
```

Перед початком зупини контейнери першої лабораторної (`vaccinations-pr1`) та закрий зайві програми: генератор і Docker використовують один комп’ютер.

Сценарій спочатку калібрує генератор через `/noop`, потім виконує ступінчасті прогони на 1, 2, 3 і 4 екземплярах, зберігає метрики, таблиці, графіки й перевіряє SIGTERM. Запуск може тривати досить довго: час залежить від того, на якому навантаженні сервіс перестане встигати обробляти запити. Під час серії не запускай інше навантаження на цьому комп’ютері.

Генератор працює у двох дочірніх процесах з асинхронним HTTP-клієнтом; кожен отримує свою частину спільного розкладу. На Windows час додатково перевіряється після спрацювання таймера, щоб запит не пішов раніше розкладу. CPU та пам’ять генератора вимірюються разом для основного процесу й усіх дочірніх процесів.

Профіль: 10 с прогріву на 200 rps; далі 20-секундні сходинки 200, 400, 600… rps. Для кожної сходинки беруться останні 15 с. Після двох сходинок нижче 90% цілі прогін зупиняється. В усіх запитів тайм-аут 5 с; затримка відраховується від запланованого часу відправки.

У калібрування є запобіжна межа 20000 rps. Якщо її досягнуто без насичення, результат **не приймається за G**. Потрібно повторити з більшою межею, наприклад:

```powershell
.\.venv\Scripts\python.exe scripts/experiment.py --safety-max-rate 40000
```

Якщо після вилучення обмежених генератором точок немає двох придатних N>1 або обмежена точка N=1, сценарій повторює серію з 0.75 CPU на web. Пам’ять і пул не змінюються. Обидві серії зберігаються окремо; вибрана серія вказана в `results/selected-series.json`.

Якщо генератор відстає у прогонах сервісу, сценарій зберігає діагностику та завершується з помилкою. Критерії контролю: фактично почато не менше 98% цільових запитів, p95 затримки відправки не більше 100 мс. Такі дані не використовуються для розрахунку USL. Якщо й після зменшення CPU вимірювань недостатньо, потрібен швидший генератор.

Перед повторною повною серією старі `results/` переміщуються в `history/`. Базу та том Prometheus сценарій не видаляє. У кожній серії додається 100 записів, а запити читання використовують ідентифікатор з цього набору. Повторний запуск може залишити записи минулої серії в таблиці; це зазначається при описі умов вимірювання.

## Що отримується після запуску

- `results/noop.json` — сирі запити калібрування.
- `results/cpu-*/run-N.json` — запити, посекундні результати й незалежні заміри незавершених запитів.
- `results/cpu-*/prometheus-N.json` — експорт часових рядів і бакетів за сходинками.
- `results/cpu-*/run-N.resources.jsonl` — знімки docker stats, CPU і сумарного RSS усіх процесів генератора та CPU хоста.
- `results/cpu-*/targets-N.json` — стан цілей; `lb-N.log` містить лише період відповідного прогону.
- `results/graceful-check.json` — код завершення зупиненого контейнера й помилки за 10 с навколо зупинки.
- `RESULTS.md` — числові таблиці, підстановки у формули та графіки.
- `figures/` — графіки навантаження, затримок, метрик екземплярів, дроселювання та USL.

Щоб заново обчислити таблиці та графіки зі збережених файлів:

```powershell
.\.venv\Scripts\python.exe scripts/analyze.py
```

Скрипт `analyze.py` оновлює таблиці в `RESULTS.md` і графіки. Після нового запуску також потрібно оновити пояснення та висновки в `REPORT.md`. Стан чотирьох цілей UP збережено у відповіді API Targets; додатково можна додати скриншот цієї сторінки.

## Організація GitHub

Створи окремий порожній публічний репозиторій **pr2-metrics**. Для завантаження підготуй папку `submission` командою з наступного розділу, щоб не відправляти великий noop.json одним файлом. У репозиторії мають залишитися папки `scripts/`, `tests/`, `results/` і `figures/`. Перша робота залишається в `pr1-CRUD--`. Для третьої роботи пізніше буде окремий репозиторій. `.env`, `.venv`, `history/` і ZIP не завантажуються.

Зупинка без видалення результатів: `docker compose down`. Команда `docker compose down -v` видаляє базу та часові ряди Prometheus; застосовуй її після експорту метрик і побудови графіків.

## Захист сервісу від переповнення черги

Одночасно до CRUD-обробників допускається не більше 64 запитів на екземпляр (`MAX_INFLIGHT_REQUESTS`). Якщо всі обробники зайняті, нові запити отримують 503 з полем `capacity`. Ці відповіді враховуються як помилки. Генератор при цьому продовжує надсилати запити за розкладом. `/metrics`, `/livez` та `/healthz` не блокуються цією чергою. Балансувальник не повторює 503 на іншому екземплярі, тому відмова через заповнення черги не множить навантаження. Пул бази залишається на 15 з’єднань.

Для запуску зі збереженням вікна PowerShell після завершення або помилки:

```powershell
powershell -NoExit -ExecutionPolicy Bypass -File .\run-lab.ps1
```

## Підготовка файлів для GitHub

`results/noop.json` займає приблизно 206 МБ, тому його не слід перетягувати в GitHub як один файл. Для підготовки папки здачі виконай у корені проєкту:

```powershell
.\.venv\Scripts\python.exe scripts/package_submission.py
```

З’явиться папка `submission`. Завантаж **її вміст**, а не саму зовнішню папку, у порожній репозиторій `pr2-metrics`. У вебінтерфейсі зручно завантажувати кореневі файли та папки кількома окремими порціями, зберігаючи структуру. Скрипт копіює код, звіт, графіки і результати, пропускає `.env`, `.venv`, `.git` та `history`. Великий файл калібрування ділиться на стиснені JSON-масиви по 50000 записів у `results/noop-raw/`. Самі записи не змінюються. Решта полів і початкова SHA256 зберігаються в `metadata.json`. Початковий локальний `results/noop.json` залишається на місці.

У завантаженій копії його можна відновити командою `python scripts/restore_raw.py`. Відновлення перевіряє збіг SHA256 з початковим файлом і не перезаписує наявний `noop.json`. Для повторного створення папки здачі спочатку перейменуй або видали лише попередню згенеровану папку `submission`.
